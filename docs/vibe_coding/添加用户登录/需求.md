# 添加用户登录与账号数据归属

> 版本：v0.3
> 状态：已实施决议
> 适用范围：`apps/web` Web 应用
> 目标读者：产品、设计、前后端开发、测试

> 当前决议（覆盖本文早期游客方案）：Web 业务强制登录，不提供游客模式、`client_id` 身份或旧数据迁移；旧 session 档案和游客数据不再兼容。`wenjia_agent` SDK/CLI 仍可由外部调用方自行传入 `user_id`。

## 1. 背景与问题

当前 Web 应用是免登录模式：

- 对话历史保存在当前浏览器的 `localStorage` 中；
- Agent 会话和人物档案以 `session_id` 关联；
- 跨会话长期记忆以浏览器生成的 `client_id` 关联；
- 当前长期记忆会保存 `kind=profile` 的档案副本，人物档案与记忆边界混乱，容易出现重复、更新不同步和误删；
- 后端信任前端传入的 `session_id` 和 `client_id`，没有真正的用户身份和资源权限校验。

这导致用户更换浏览器、清理缓存或更换设备后，无法继续访问原有对话、档案和长期记忆；同时也无法可靠证明某个档案或记忆属于谁。

**需要解决的问题：如何让 Web 用户通过一个账号持续、安全地维护人物档案和长期记忆，并让两类数据各自独立、按需协作，同时不让账号系统侵入可独立复用的 Agent 核心。**

## 2. 目标用户与核心场景

### 2.1 目标用户

- 经常使用问甲、希望长期保存本人资料和分析记录的个人用户；
- 需要为家人、伴侣、朋友等多人维护档案并反复进行命盘、关系或起名分析的用户；
- 需要在多个设备登录并持续维护账号数据的用户。

### 2.2 核心场景

1. 用户注册并登录账号。
2. 用户在账号下创建和维护本人、父母、伴侣、子女、朋友等多个人物档案。
3. 新建对话时，用户可选择一个或多个人物档案作为本次分析上下文。
4. 用户在另一台设备登录后，仍可看到自己的档案、对话和长期记忆。
5. 未登录用户先完成注册或登录，登录后才能进入工作台。
6. 用户可删除自己的档案、对话和长期记忆，其他用户不能读取或修改这些数据。
7. 用户可单独管理系统长期记住的偏好和持续性上下文，不会在长期记忆中看到一份重复的人物档案。

## 3. 成功标准

### 3.1 用户结果

- 注册用户可在两个不同浏览器中访问一致的人物档案、对话列表和长期记忆。
- 创建档案后，无需在每次新对话中重复输入完整出生资料。
- 未登录状态不能访问业务数据；账号数据只按服务端会话归属。

### 3.2 系统结果

- 登录用户的数据以服务端认证得到的 `user_id` 为最终归属依据，不再信任请求体中的 `client_id`。
- 任意账号都不能通过猜测或修改资源 ID 访问其他账号的数据。
- 人物档案是出生资料的唯一事实来源，由独立档案模块管理，不再写入或复制到长期记忆。
- 长期记忆只保存非档案类的稳定偏好和持续性上下文，并提供独立的写入、查询、修改和删除逻辑。
- 所有 Web 业务能力强制登录，且 `wenjia_agent` 核心模块仍不依赖 Web 账号模型。

## 4. 方案选择

| 方向 | 说明 | 价值 | 成本与风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 继续使用 `client_id` | 把浏览器 ID 当作用户 ID，仅增加登录页面 | 改动小 | 不能证明身份，跨设备和权限问题没有真正解决 | 不采用 |
| B. Web 层自建轻量账号 | 账号作为数据所有者，Agent 运行时只接收解析后的 `user_id` | 可控、可测试，符合当前单体架构 | 需要认证、迁移和权限改造 | **MVP 推荐** |
| C. 接入第三方身份服务 | 使用 Auth0、Clerk、Supabase Auth 等 | 社交登录和账号安全能力完整 | 引入外部依赖、费用及部署复杂度 | 后续按运营需求评估 |

**推荐方向：在 `apps/web` 内实现轻量账号与服务端会话认证。账号属于 Web 产品层，`wenjia_agent` 继续只接收调用方提供的稳定 `user_id`，不感知注册、密码或登录状态。**

## 5. MVP 范围（P0）

### 5.1 注册、登录与退出

- MVP 使用“用户名 + 密码”注册和登录，不依赖短信或邮件服务。
- 用户名全局唯一，去除首尾空格后按不区分大小写规则判重。
- 密码长度至少 8 位，服务端只保存安全哈希，不保存或记录明文密码。
- 注册必须二次输入密码，只有两次输入完全一致时才创建账号。
- 注册成功后自动进入登录状态。
- 登录失败统一提示“用户名或密码错误”，避免泄露账号是否存在。
- 支持获取当前登录用户、退出当前设备，以及登录过期后的重新登录。
- 登录成功后返回到用户登录前所在页面，不丢失尚未发送的输入内容。

### 5.2 账号可绑定的数据

| 数据 | MVP 行为 | 用途 |
| --- | --- | --- |
| 人物档案 | 一个账号可维护多个档案 | 跨对话复用出生资料、命盘和关系身份 |
| 对话 | 对话归属于账号并保存标题、消息和更新时间 | 跨设备查看和继续历史对话 |
| 长期记忆 | 以账号为归属，只保存非档案类的稳定偏好和持续性上下文 | 新会话复用用户明确要求记住的信息 |
| 登录会话 | 记录有效登录设备/会话，支持过期和注销 | 安全认证 |

报告收藏、订阅与支付等不属于本次 MVP，见第 8 节。

### 5.3 档案与长期记忆的模块边界

| 模块 | 负责的数据 | 写入来源 | Agent 使用方式 | 明确禁止 |
| --- | --- | --- | --- | --- |
| `ProfileModule` | 姓名、关系、性别、出生信息、命盘结果 | 档案表单、排盘结果经用户确认保存 | 用户显式选择档案后，以结构化上下文注入 | 把档案复制成长期记忆 |
| `MemoryModule` | 回答偏好、长期目标、持续关注事项、用户纠正 | 用户明确要求记住，或在记忆管理页手动创建 | 按当前问题检索少量相关记忆 | 保存出生资料、四柱、五行或人物关系档案 |
| `ContextAssembler` | 不持久化业务数据 | 读取本轮选中的有效档案和相关记忆 | 分区组装为“人物档案上下文”和“用户长期记忆” | 把两类数据合并后回写任一模块 |

- 两个模块拥有独立的数据表、仓储、服务、API 和测试，不能通过共享一张表或 `kind` 字段伪装成逻辑分离。
- `ProfileModule` 的账号归属字段为 `user_id`，`session_id` 只能作为可选来源信息，不能继续作为档案所有权依据。
- `MemoryModule` 不得依赖 `ProfileModule` 的创建、修改或删除事件来维护档案副本。
- Agent 需要人物资料时查询 `ProfileModule`；需要用户偏好或持续上下文时查询 `MemoryModule`。

### 5.4 人物档案模块

#### 5.4.1 数据与能力

- 档案字段沿用现有模型：姓名、与账号用户的关系、性别、出生日期时间、历法、闰月、出生地、经度、四柱和五行等。
- 档案至少包含 `id`、`user_id`、业务字段、`created_at`、`updated_at` 和 `deleted_at`；`deleted_at` 为空表示有效档案。
- 关系支持“本人、父亲、母亲、伴侣、子女、朋友、其他”；“其他”允许填写自定义关系名称。
- 每个账号最多有一个有效的“本人”档案，其他关系可有多个，使用姓名进行区分。
- 模块提供独立的创建、列表、详情、修改、软删除和恢复能力。
- 新对话可选择一个或多个人物档案；关系分析至少选择两个档案，单人分析默认优先使用有效的“本人”档案。

#### 5.4.2 CRUD 规则

- **创建**：创建账号级档案，不要求绑定具体对话；相同关系和姓名允许存在，但前端应提示可能重复。
- **查询**：默认只返回 `deleted_at IS NULL` 的档案；详情查询也必须校验 `user_id`。只有回收站或恢复场景可显式查询已删除档案。
- **修改**：只允许修改当前账号的有效档案；修改出生日期、时间、历法或地点后，旧四柱和五行必须失效，并在下次使用时重新计算。
- **删除**：删除为软删除，只设置 `deleted_at` 和 `updated_at`，不得删除数据库记录，不得改变档案 ID，重复删除保持幂等。
- **恢复**：清空 `deleted_at`；恢复前重新校验“本人”唯一性及其他业务约束，冲突时提示用户处理，不静默覆盖。
- **物理删除**：普通档案操作不提供物理删除；仅在注销账号或满足明确的数据清理策略时由系统执行。

#### 5.4.3 软删除后的行为

- 已删除档案不出现在默认列表、档案选择器、Agent 档案查询工具和新对话上下文中。
- 已删除档案不能被修改或关联到新对话；相关操作按资源不存在处理。
- 历史对话保留当时使用的档案名称和必要展示快照，不因软删除而破坏历史消息。
- 历史关联可继续保存原 `profile_id`，但不得据此把已删除档案重新注入 Agent。
- MVP 不自动清理已软删除档案；用户可在档案回收站查看并恢复。

### 5.5 长期记忆模块

#### 5.5.1 记忆定义

长期记忆用于减少跨会话重复说明，只保存对后续多次对话仍有价值、且用户明确希望系统记住的非档案信息。

MVP 支持以下类型：

| 类型 | 示例 | 是否允许 |
| --- | --- | --- |
| `preference` 回答偏好 | “以后先给结论”“回答尽量简洁” | 允许 |
| `goal` 持续目标 | “近期持续关注职业方向” | 允许 |
| `context` 长期上下文 | “接下来的讨论以转岗准备为背景” | 允许 |
| `correction` 用户纠正 | “不要把娱乐性分析表述为确定结论” | 允许 |
| 人物档案 | 姓名、关系、出生时间、地点、四柱、五行 | **禁止，必须进入档案模块** |
| 临时信息 | 只对当前一轮有效的要求或问题 | 禁止长期保存 |
| 敏感凭证 | 密码、令牌、身份证号、银行卡等 | 禁止保存 |

#### 5.5.2 写入与更新

- MVP 仅在用户明确表达“记住”“以后都这样回答”等持久化意图，或用户在管理页面手动创建时写入长期记忆。
- 系统不得仅凭模型推断自动永久保存记忆；自动提取候选记忆属于 P1，且保存前需要用户确认。
- 写入前进行分类和内容检查；疑似人物档案信息引导用户创建或更新档案，不写入 `MemoryModule`。
- 每条记忆包含稳定 ID、`user_id`、类型、标题、内容、来源会话、创建时间和更新时间；可预留 `expires_at`，MVP 默认不过期。
- 语义相同的记忆优先更新已有记录；无法确定是否重复时保留两条并允许用户整理，不由模型静默覆盖。

#### 5.5.3 查询、注入与删除

- 用户可查看、新建、编辑和删除自己的长期记忆；记忆管理界面不展示人物档案。
- 每轮运行按当前问题检索相关记忆，并受最大条数和最大字符数限制；无关记忆不注入 Agent。
- 记忆内容作为不可信用户数据注入，不得执行其中包含的指令或覆盖系统安全规则。
- 删除记忆后立即停止检索和注入。与档案的软删除不同，记忆删除默认物理删除；如需审计，只保留不含正文的删除事件。
- 删除或修改长期记忆不影响任何人物档案；删除或修改人物档案也不触发长期记忆写入、更新或删除。

### 5.6 运行时上下文组装

- 前端在发起聊天时传递用户本轮显式选择的 `profile_id` 列表，不传完整档案作为可信数据。
- 服务端通过认证身份校验档案归属与 `deleted_at IS NULL`，再读取结构化档案。
- 服务端独立查询与本轮问题相关的长期记忆。
- `ContextAssembler` 将两类数据分区组装后交给 Agent：档案用于确定性排盘和人物分析，长期记忆用于调整回答方式及补充持续上下文。
- 同名人物、相似记忆或历史消息都不能替代显式选择的档案 ID。
- Agent 工具保存排盘结果时只更新对应档案记录，不再调用 `remember_profile` 或创建 `kind=profile` 的记忆。

### 5.7 对话归属与跨设备同步

- 登录用户新建的每个 `session_id` 必须登记所属 `user_id`；服务端在读取、继续或删除对话前校验归属。
- 对话列表及可见消息从仅保存在 `localStorage` 改为以服务端数据为准，本地只允许作为缓存。
- 在另一设备登录后，可查看、继续和删除该账号下的历史对话。
- 对话关联档案时保存档案 ID；展示历史消息时可保留当时使用的档案名称快照，但后续分析使用最新档案数据。
- 删除对话不默认删除人物档案或长期记忆；界面应明确说明影响范围。

### 5.8 登录门槛与数据边界

- 未登录用户不能发起对话、读取或修改人物档案、长期记忆及建议接口；前端必须先展示登录/注册入口。
- 所有业务数据只归属于服务端认证账号，不接受浏览器生成的 `client_id` 或其他临时身份。
- 退出登录后，前端必须清除或隔离当前账号的本地缓存，不能让下一个使用该浏览器的人直接看到账号数据。

### 5.9 重新部署与旧数据

- 本版本不兼容旧游客数据、旧 session 档案路由和旧 `client_id` 关联数据。
- 部署前由运维备份并按需清理旧表；应用启动只创建当前认证模型，不执行游客数据导入或隐式迁移。

### 5.10 账号数据删除

- 用户可分别软删除人物档案、物理删除长期记忆以及删除对话。
- 用户可注销账号；注销前要求再次验证密码并明确提示影响范围。
- 注销后撤销全部登录会话，并删除账号、档案、长期记忆、对话归属及可识别的消息数据。
- 安全审计日志可按配置保留，但不得保留密码、完整出生资料或对话正文。

## 6. 权限与安全要求

1. 服务端从认证会话解析 `user_id`；请求体不得携带用于归属判断的临时身份字段。
2. 所有档案、记忆、对话的读写操作都必须同时校验资源 ID 和所属 `user_id`，防止越权访问。
3. 认证凭证使用 `HttpOnly` Cookie；生产环境启用 `Secure`，`SameSite` 至少为 `Lax`，不得把长期凭证放入 `localStorage`。
4. 登录会话使用高熵随机令牌，数据库只保存令牌哈希；会话有明确过期时间，退出后立即失效。
5. 密码使用 Argon2id、bcrypt 等专用算法哈希，并设置合理成本参数。
6. 注册和登录接口需要按 IP 与账号维度限流；连续失败不得导致服务器高成本调用。
7. Cookie 认证的状态变更接口必须具备 CSRF 防护；CORS 只允许配置的可信来源。
8. API 响应、日志和 trace 中不得出现密码、会话令牌或完整认证 Cookie。
9. 数据库结构变更使用可回滚的迁移脚本，不以线上 `create_all` 代替正式迁移。
10. 账号认证不可阻断 `wenjia_agent` 作为 SDK/CLI 被外部系统使用；外部调用方仍可自行提供 `user_id`。

## 7. 关键交互

### 7.1 未登录状态

- 顶部或侧栏显示明确的“登录”入口。
- 未登录用户只能看到登录/注册界面，不能进入业务工作台。

### 7.2 登录状态

- 展示当前用户名和账号菜单，至少包含“人物档案”“长期记忆”“账号设置”“退出登录”。
- “人物档案”进入独立档案模块，支持有效档案列表、创建、编辑、软删除和回收站恢复。
- “长期记忆”只展示偏好、目标、持续上下文和纠正，不混入人物档案。
- 新建对话时可快速选择有效档案；没有档案时提供创建入口。
- 登录过期时保留当前未发送草稿，完成登录后恢复操作。

### 7.3 错误状态

- 网络错误、凭证过期、迁移冲突和权限拒绝必须有可理解的提示。
- `401` 表示需要登录或登录已过期；`403` 表示已登录但无权操作；不存在或不属于当前用户的资源统一按 `404` 处理，避免泄露资源存在性。

## 8. 后续范围（P1/P2）

### P1

- 绑定并验证邮箱，用于找回密码和安全通知；
- 修改用户名、修改密码、查看并注销其他设备；
- 从对话中提取候选长期记忆，并在用户确认后保存；
- 长期记忆过期时间、暂停使用、批量整理和冲突合并；
- 报告收藏、标签、搜索和导出；
- 档案头像、备注和分组；
- 档案回收站的批量恢复和按保留策略清理。

### P2

- 微信、Apple、Google 等第三方登录；
- 家庭成员共同维护或只读分享档案；
- 多租户、团队空间和角色权限；
- 会员、订阅、支付与使用额度；
- 可选的向量记忆和用户自助数据导出。

## 9. 本次明确不做

- **不在 Agent 核心实现账号系统**：认证属于 Web 产品层，保持核心库可嵌入。
- **强制登录**：业务数据和 Agent 对话必须绑定服务端认证账号。
- **不在 MVP 接入短信、邮件或第三方登录**：这些能力需要额外服务和运营成本。
- **不做档案公开分享或协作编辑**：涉及更复杂的授权、撤销和隐私规则。
- **不把人物档案保存为长期记忆**：人物资料只存在于档案模块，由本轮显式选择后使用。
- **不让模型自动永久保存推断结果**：MVP 只保存用户明确要求记住或手动创建的内容。
- **不在普通档案删除中物理清除记录**：档案使用软删除，物理清理由账号注销或独立数据策略处理。
- **不同时引入支付、会员和运营后台**：避免认证改造扩大为完整商业系统。

## 10. 验收标准

### 10.1 认证

- [ ] 用户可使用合法用户名、密码和确认密码注册；缺少确认密码或两次输入不一致时不能创建账号，重复用户名得到明确但不泄露敏感信息的错误。
- [ ] 注册后自动登录；刷新页面后，在会话有效期内仍保持登录。
- [ ] 正确凭证可登录，错误凭证不能登录，登录失败响应不区分用户名不存在或密码错误。
- [ ] 退出后原会话令牌立即失效，再访问账号资源返回 `401`。
- [ ] 密码和原始会话令牌不以明文出现在数据库、日志或 API 响应中。

### 10.2 数据归属

- [ ] 用户 A 无法通过修改档案、记忆或会话 ID 读取、修改、删除用户 B 的数据。
- [ ] 登录用户的 API 不使用前端提交的 `client_id` 决定资源归属。
- [ ] 用户在设备 A 创建的档案和对话，能在设备 B 登录后查看和继续使用。
- [ ] 退出登录后，当前浏览器不再展示上一账号的缓存数据。

### 10.3 人物档案模块

- [ ] 一个账号可创建多个不同关系的人物档案，但同时只能有一个有效的“本人”档案。
- [ ] 档案具备创建、列表、详情、修改、软删除和恢复能力，所有操作均校验账号归属。
- [ ] 删除档案只设置 `deleted_at`，数据库记录和档案 ID 保留，重复删除结果一致。
- [ ] 默认查询、档案选择器和 Agent 工具都不会返回已软删除档案。
- [ ] 已删除档案不能被修改或用于新对话，恢复后可重新使用。
- [ ] 恢复“本人”档案时会重新校验唯一性，冲突不会被静默覆盖。
- [ ] 修改出生信息后旧命盘失效，并能重新计算。
- [ ] 历史对话仍可展示已删除档案的名称快照，但不会把该档案重新注入 Agent。

### 10.4 长期记忆模块

- [ ] 长期记忆中不存在新写入的 `kind=profile` 记录，也不保存姓名、关系、出生信息、四柱或五行等档案字段。
- [ ] 创建、修改或删除档案不会创建、修改或删除任何长期记忆。
- [ ] 用户明确要求记住偏好或持续上下文时，系统可保存为正确类型的长期记忆。
- [ ] 用户可查看、新建、编辑和删除自己的记忆，且记忆管理页不展示人物档案。
- [ ] 删除记忆后，该内容不再出现在后续 Agent 上下文中。
- [ ] 每轮只注入与问题相关且未超过条数、字符限制的记忆。
- [ ] 同一轮可同时使用用户显式选择的有效档案和检索出的相关记忆，二者上下文边界清晰。

### 10.5 未登录与旧数据

- [ ] 未登录访问聊天、档案、长期记忆和建议接口统一返回 `401`。
- [ ] 请求体不接受 `client_id` 或其他临时身份字段。
- [ ] 旧游客数据、旧 session 档案路由和旧 `kind=profile` 数据不参与当前应用运行。

### 10.6 工程质量

- [ ] 后端具备认证、权限、档案 CRUD/软删除、记忆逻辑和未登录拒绝的单元测试与 API 集成测试。
- [ ] 前端具备注册、登录、退出、登录过期和缓存隔离测试。
- [ ] 数据库初始化只创建当前认证模型，不执行旧游客数据导入。
- [ ] `poetry run pytest`、`poetry run ruff check . --no-cache`、前端测试及构建全部通过。

## 11. 关键假设与验证方式

- [ ] **用户愿意注册以换取跨设备保存。** 在登录入口展示“同步档案与对话”，记录游客到注册的转化和放弃节点。
- [ ] **用户名密码足以支撑 MVP。** 上线前访谈目标用户；若密码找回需求强烈，应把验证邮箱提前到 P0。
- [ ] **用户主要以账号私有方式维护档案。** 观察是否频繁出现家庭共享诉求，再决定是否设计共享权限。
- [ ] **用户能理解档案与长期记忆的区别。** 用界面文案和可用性测试确认用户知道出生资料应进入档案、回答偏好应进入记忆。
- [ ] **显式保存能覆盖 MVP 的主要记忆需求。** 检查用户是否频繁期待系统自动记住内容，再决定何时引入候选记忆提取。

## 12. 待确认问题

1. MVP 是否继续采用“用户名 + 密码”，还是上线即要求“邮箱 + 密码 + 邮箱验证”？当前文档推荐前者以减少外部依赖。
2. 游客对话的服务端 Agent 消息是否设保留期限？建议配置默认期限，并在游客界面明确说明。
3. 注销账号后，运行 trace 和安全审计日志分别保留多久、如何去标识化？
4. 历史对话中的档案展示应完全保留当时快照，还是始终展示最新名称？当前建议“展示保留快照，后续运行使用最新数据”。
5. 已软删除档案是否永久保留，还是在 30/90 天后物理清理？当前建议 MVP 不自动清理，待数据保留策略确认。

## 13. 与现有文档的范围关系

现有 `docs/REQUIREMENTS.md` 和 `docs/ARCHITECTURE.md` 将账号、登录认证列为非目标。本需求获确认后，应把该边界更新为：

- `wenjia_agent` 核心仍不提供账号、认证、支付和多租户能力；
- `apps/web` 作为产品示例可以实现轻量账号、认证和用户数据持久化；
- SDK/CLI 调用方式和由外部调用方提供 `user_id` 的能力保持兼容。
