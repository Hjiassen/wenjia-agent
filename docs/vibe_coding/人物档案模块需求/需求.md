# 人物档案模块需求

> 版本：v1.0
> 状态：开发中
> 适用范围：`apps/web` Web 应用的人物档案、对话上下文与待补充人物
> 目标读者：产品、交互/UI、前后端开发、测试

## 1. 背景

人物档案承载用户本人及其关联人物的出生资料，是排盘、单人分析和关系分析的结构化数据来源。当前模块已支持账号级档案的表单创建、编辑、选择、软删除和恢复；但仍有两个关键断点：

1. 用户没有“本人”档案时，系统没有在合适的时机明确引导其补充，后续分析容易反复追问基础资料。
2. 对话中提到了父母、伴侣、子女或朋友等新人物时，系统只能依赖用户主动打开档案面板创建，容易遗漏，也不应未经确认直接保存敏感资料。

本次通过重新梳理信息架构与交互流程，使人物档案成为可持续维护、可在对话中自然补充、且始终由用户掌控的数据模块。

## 2. 目标与原则

### 2.1 产品目标

1. 当账号没有有效的“本人”档案时，引导用户以对话或表单两种方式完成创建。
2. 当对话中出现可能需要建档的非本人时，生成可管理的“待补充人物”候选，不自动写入正式档案。
3. 用户可以从候选快速进入预填表单或继续对话补充，并在确认后加入自己的档案列表。
4. 保持现有档案的账号隔离、显式选择注入、出生资料校验和软删除行为。

### 2.2 设计原则

- **用户确认优先**：对话识别只能创建候选，不能自动建立正式人物档案或保存推测出的出生信息。
- **档案优先于记忆**：姓名、关系、出生日期时间、地点、四柱、五行等人物资料只进入档案模块，不写入长期记忆。
- **姓名显式输入**：涉及人物资料、排盘或人物分析的对话，必须由用户明确输入分析对象的姓名；关系称谓、代词和系统默认名称不能替代姓名。
- **关系确认与枚举归类**：涉及人物资料、排盘或人物分析的对话，必须由用户确认该对象与本人的关系；系统只能在确认后写入固定 `relationship_type` 枚举，不能根据称谓或上下文自行归类。
- **渐进补全**：允许先建立信息不完整的档案；需要排盘或依赖出生资料分析时，再明确提示缺失字段并引导补齐。
- **最少打扰**：同一对象在同一会话内只提示一次；用户忽略或关闭后，不在本轮重复打断。
- **显式上下文**：只有用户在本轮主动附加的有效档案，才能作为 Agent 的可信人物上下文。

## 3. 范围

### 3.1 本期范围（P0）

- 本人档案缺失检测与创建引导。
- 表单创建、对话创建两条建档路径。
- 从对话中识别非本人候选人物，并进入待补充列表。
- 待补充人物的查看、编辑名称和关系、忽略、转为正式档案、继续对话补充。
- 同步重新设计桌面端与手机端的档案入口、聊天选择器、列表、详情/编辑、待补充列表和空状态。
- 与现有档案选择器、排盘结果保存、软删除/恢复和账号权限逻辑的衔接。

### 3.2 非本期范围

- 从聊天文本中自动推断或补全出生日期、时辰、地点等敏感资料。
- 自动把候选人物或聊天内容写入长期记忆。
- 修改命理计算、排盘算法或报告生成逻辑。

档案增强、候选管理、档案文本复制与待确认字段纳入第 11 节 P1；导入导出、公开分享、跨账号访问、跨账号候选推荐及未授权自动建档仍不在范围内。

## 4. 用户与核心场景

| 用户 | 场景 | 期望结果 |
| --- | --- | --- |
| 新用户 | 首次进入工作台，尚未创建本人档案 | 明确知道为何需要本人档案，并可选择表单或对话完成创建 |
| 已登录用户 | 输入需要本人出生资料的问题，但没有本人档案 | 在不丢失当前问题的前提下补档，完成后继续原问题 |
| 已有档案用户 | 在对话中提到“我妈妈”“我对象”或具体姓名的新人物 | 系统给出轻量候选提醒，用户决定是否加入待补充列表 |
| 用户 | 想为候选人物补齐资料 | 可从候选直接打开预填表单，或进入带上下文的对话收集资料 |
| 用户 | 候选识别有误或暂不处理 | 可忽略；不会生成正式档案，也不会在当前会话重复提醒 |

## 5. 信息架构与状态

### 5.1 页面、入口与职责边界

人物档案采用“聊天选择器 + 独立管理模块”的双入口结构，两者不得混合职责：

| 入口 | 位置 | 允许的操作 | 明确禁止 |
| --- | --- | --- | --- |
| 聊天档案选择器 | 桌面端当前对话框左侧弹层；手机端聊天工具栏入口打开的底部抽屉 | 查看有效正式档案、选择/取消选择本轮档案、清空本轮选择、确认选择 | 新增、编辑、删除、恢复、处理候选、复制档案文本或跳转到编辑表单 |
| 人物档案模块 | 桌面端工作台主导航；手机端主导航或账号菜单中的“人物档案”入口 | 查看、新增、编辑、删除、恢复、处理候选、复制及其他档案管理 | 代替聊天选择器隐式改变当前对话已选档案 |

人物档案模块应提供以下结构：

| 区域 | 内容与操作 |
| --- | --- |
| 档案概览 | 本人档案状态、有效档案数量、待补充数量；没有本人档案时显示优先级最高的补档入口 |
| 我的档案 | 有效档案列表，支持查看、编辑、新增和移入回收站 |
| 待补充 | 仅展示未处理的候选人物，支持“补充资料”“通过对话补充”“忽略” |
| 回收站 | 展示已软删除档案，支持恢复；不展示候选人物 |
| 创建/编辑页面 | 在人物档案模块内填写人物基础资料和出生资料；保存后返回档案列表并刷新状态 |

待补充数量为零时，入口可以弱化为普通标签；大于零时显示数字标记。候选人物不得与正式档案混排，避免用户误以为已保存。

### 5.2 状态定义

正式档案沿用现有状态：`有效`、`已删除`。新增候选人物独立管理，状态如下：

| 候选状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| `pending` | 已从对话产生，等待用户处理 | 补充资料、通过对话补充、编辑、忽略 |
| `converted` | 已由用户确认并创建正式档案 | 不再出现在待补充默认列表，保留来源关联用于审计/去重 |
| `dismissed` | 用户明确忽略 | 不再主动展示；同一会话内不再提示相同候选 |

候选人物不是档案：不能在档案选择器中附加，不能注入 Agent，不能参与排盘或关系分析。

## 6. 功能需求

### 6.1 本人档案缺失引导

#### 触发条件

当当前账号不存在有效的 `relationship_type=本人` 档案时，满足下列任一条件即可触发引导：

1. 用户首次进入人物档案模块。
2. 用户在空档案状态下发起新对话。
3. 用户的问题涉及本人命盘、运势、起名、事业、感情或其他需要本人出生资料的分析。
4. 用户尝试进行单人分析且未附加任何有效档案。

#### 交互要求

- 首次触发使用明确但可关闭的提示，说明“创建本人档案后可复用出生资料，减少重复填写”。
- 提供两个同级操作：`表单填写` 与 `通过对话创建`，以及 `暂不创建`。
- `表单填写` 跳转到人物档案模块中关系预设为“本人”的创建页面，不在聊天档案选择器内打开表单。由聊天场景触发时应携带安全的返回标识；保存成功后返回原对话、附加该档案并恢复用户原本待发送的问题。
- `通过对话创建` 进入人物档案模块内的建档对话流程，而不是在聊天档案选择器内新增。系统应保留原问题，并由 Agent 按缺失字段收集姓名、性别、出生日期、出生时间、历法、出生地等信息；信息完整并经用户确认后保存正式档案。
- `暂不创建` 不阻止普通闲聊；若用户继续发起依赖出生资料的分析，应提示无法完成分析的原因，并再次提供两种创建入口。
- 用户在一个会话中关闭引导后，除非主动进入档案模块或再次发起依赖出生资料的分析，否则不重复展示。

### 6.2 表单建档与编辑

- 创建表单包含：姓名、与账号用户的关系、性别、历法、出生日期、出生时间、闰月（仅农历）、出生省市；经度由系统根据地点处理或作为高级信息展示。
- 关系选项为：本人、父亲、母亲、伴侣、子女、朋友、其他；选择“其他”时必须填写自定义关系名称。
- 姓名和关系为建档必填项；出生资料允许暂缺，但在用户提交不完整资料时要显示“暂不能排盘”的状态说明。
- 正式档案的 `relationship_type` 只能保存以下枚举。关系文本由用户确认后按表映射；无法确定或不在表内的关系必须选择“其他”，并填写 `custom_relationship`，不得新增或拼接新的枚举值。

| 用户确认的关系 | `relationship_type` 枚举 | 补充规则 |
| --- | --- | --- |
| 本人 / 我自己 | `本人` | 每个账号最多一个有效档案 |
| 父亲 / 爸爸 | `父亲` | 仅在用户确认后映射 |
| 母亲 / 妈妈 | `母亲` | 仅在用户确认后映射 |
| 配偶 / 丈夫 / 妻子 / 恋人 | `伴侣` | 不根据称谓、性别或上下文自动判定 |
| 儿子 / 女儿 / 孩子 | `子女` | 不区分子女性别 |
| 朋友 | `朋友` | 同事、同学等不自动归入此项 |
| 其他亲属、同事、同学等 | `其他` | `custom_relationship` 必填 |

- 每个账号最多存在一个有效的“本人”档案。创建、编辑或恢复导致冲突时，阻止保存并引导用户编辑或删除已有本人档案。
- 出生日期、时间、历法、地点或经度变更后，已有四柱、五行和排盘上下文必须失效，界面显示“出生资料已更新，需重新排盘”。
- 从人物档案模块主动创建时，仅加入档案列表，不自动创建、切换或修改聊天会话；仅当用户由某个聊天缺档引导进入且保存成功时，返回原对话并附加新档案。

### 6.3 对话式建档

- 建档对话应明确当前要创建的人物及关系，避免把多个对象的出生信息混合。
- 在收集其他出生资料、创建正式档案、排盘或进行人物相关分析前，Agent 必须先要求用户输入该对象的姓名。`本人`、`母亲`、`我对象`、`孩子`、`他/她`等关系称谓或代词不得作为姓名保存或用于计算。
- 用户未提供姓名时，Agent 仅追问姓名，不得以“未命名”“匿名用户”或系统生成名称创建档案、调用排盘工具或保存计算结果。用户提供姓名后，才继续收集其他缺失字段。
- 用户提供姓名后，Agent 必须询问并复述“该人物与您是什么关系？”；只有用户明确确认后才能映射为 `relationship_type`。如用户的回答无法匹配固定枚举，Agent 必须请其确认“其他”并输入关系说明。
- `relationship_type` 未确认时，Agent 不得创建正式档案、调用排盘工具或保存计算结果；已识别到的“妈妈”“对象”等称谓只能作为待确认提示，不能直接作为枚举值。
- Agent 必须按缺失字段追问，不得补造、默认或猜测出生时间、地点、农历闰月等资料。
- 用户提供完整出生信息后，先展示归纳摘要并请求确认；确认后才执行排盘和保存。
- 排盘成功后，将计算结果写入对应正式档案，并在界面刷新档案状态；若保存失败，明确提示并保留本轮已收集信息供重试。
- 用户中途取消时，不创建正式档案；已经明确添加到待补充列表的候选仍保留，除非用户另行忽略。

### 6.4 对话识别与待补充人物

#### 识别规则

- 系统仅在用户消息中识别非本人的明确人物提及，例如关系称谓加人物指代（“我妈妈”“孩子”）或明确姓名加关系（“我伴侣小王”）。
- 不识别泛称、虚构人物、公众人物、未明确指向的人物，或用户明确表示“不需要建档/不要记录”的内容。
- 每次识别生成的候选至少包含：显示名称（可为“我的母亲”等临时名称）、关系建议、来源会话 ID、来源消息 ID、创建时间和状态；不得从语义推断出生资料或将关系建议直接写入 `relationship_type` 枚举。
- 同一账号、同一会话、相同标准化名称与关系的未处理候选只保留一条；新提及可更新其最近来源时间，不重复提醒。
- 识别可由规则、模型或二者组合实现，但结果必须以“建议”呈现，且服务端必须校验账号归属与去重。

#### 提醒与确认

- 检测到候选后，在对应助手回复末尾或输入区附近展示非阻塞提示，例如“检测到你提到了‘母亲’，是否加入待补充人物？”。
- 用户可选择 `加入待补充`、`现在补充`、`忽略`。关闭提示等同于本轮不处理，不自动写入候选。
- `加入待补充` 创建 `pending` 候选并更新待补充数量；`现在补充` 先创建候选，再进入表单或对话式补充流程。
- `忽略` 将相同候选在当前会话标记为 `dismissed`，本会话不再提示。用户可在后续版本的候选历史中查看，但 P0 不要求提供恢复入口。
- 助手不得声称“已保存档案”，除非用户已确认且正式档案创建接口返回成功。

### 6.5 待补充列表

- 待补充列表默认按最近提及时间倒序展示，展示名称、关系、来源对话标题/时间和信息完整度，不展示完整聊天正文。
- 用户可编辑候选名称和关系，以纠正识别错误；编辑后重新执行去重校验。
- `补充资料` 在人物档案模块内打开预填名称和关系建议的表单；用户必须确认关系枚举（或填写“其他”的关系说明）后才能保存正式档案，并将候选置为 `converted`。
- `通过对话补充` 在人物档案模块内启动带候选标识的建档对话，Agent 只收集该候选人物的信息。
- 候选转正后，正式档案进入“我的档案”，但不自动附加到历史或当前普通对话；仅在用户从当前会话点击“现在补充”并完成时，才可询问是否附加。
- 用户可忽略候选。忽略不影响已经存在的正式档案，也不影响原始对话记录。

### 6.6 档案选择与运行时上下文

- 档案选择器只展示当前账号下未删除的正式档案；待补充候选、已删除档案均不得出现。
- 桌面端当前对话框左侧档案弹层只提供档案勾选、取消勾选、清空和确认操作；档案条目及空状态均不得出现新增、编辑、删除、恢复、复制或候选处理按钮。
- 用户从聊天档案选择器点击档案条目只改变本轮待确认选择，不进入详情或编辑页面；点击“确认”后才更新当前对话的 `profile_ids`，关闭或取消时保留上一次已确认选择。
- 用户可在每轮对话显式选择最多 8 个档案；服务端只接受档案 ID，并校验所有权和有效状态后读取结构化资料。
- 没有选择档案时，不得把候选或历史档案隐式注入 Agent。单人分析可优先推荐本人档案，但仍需用户确认选择。
- 关系分析应在用户选择至少两个有效档案后进行；不足时提示补充或选择人物。
- 对话历史可保存当轮附加档案的名称快照，仅用于展示；删除档案后，历史消息不得因此损坏，也不得重新注入已删除档案。

### 6.7 删除、恢复与隐私

- 正式档案删除采用软删除：从默认列表、选择器和 Agent 查询中移除，保留记录供回收站恢复。
- 已删除档案不能修改、不能用于新对话、不能作为候选转正的去重目标；恢复时重新校验“本人”唯一性。
- 待补充候选的忽略为逻辑隐藏，不等同于正式档案删除。
- 档案、候选、来源会话及其内容均按认证 `user_id` 隔离；不属于当前账号的资源统一返回不存在，不泄露是否存在。
- 日志、埋点和错误信息不得记录完整出生资料、会话 Cookie 或完整聊天正文。

## 7. 数据与接口约束

### 7.1 正式档案

沿用现有账号级人物档案模型，至少包含 `id`、`user_id`、姓名、关系、出生资料、排盘结果、`created_at`、`updated_at`、`deleted_at`。正式档案是人物出生资料和排盘结果的唯一事实来源。

### 7.2 待补充人物

新增独立候选数据模型，建议字段如下：

| 字段 | 说明 |
| --- | --- |
| `id` | 候选唯一标识 |
| `user_id` | 所属账号 |
| `display_name` | 用户可编辑的候选名称 |
| `relationship_type` | 用户确认后的预置关系枚举；`pending` 候选可为空 |
| `suggested_relationship` | 从对话识别出的关系建议，只用于展示和预填，不能直接作为正式枚举 |
| `custom_relationship` | 选择“其他”时的关系说明 |
| `status` | `pending`、`converted` 或 `dismissed` |
| `source_session_id` / `source_message_id` | 仅用于追溯来源与同会话去重 |
| `converted_profile_id` | 转正后的正式档案 ID，可为空 |
| `created_at` / `updated_at` / `last_mentioned_at` | 生命周期与排序字段 |

候选表不得保存完整出生资料、命理计算结果或完整聊天正文。正式档案与候选必须使用独立存储和接口，不能通过给档案表增加状态字段混用。

### 7.3 接口行为

接口路径可按现有风格实现，具体 URL 由技术设计确定；以下行为为必须满足的契约：

| 能力 | 行为 |
| --- | --- |
| 档案 CRUD | 创建、读取、更新、软删除、恢复均按认证账号校验；修改出生资料时使排盘结果失效 |
| 本人状态查询 | 返回当前账号是否存在有效本人档案，供前端决定引导状态 |
| 候选创建 | 仅在用户点击“加入待补充”或“现在补充”后创建，不接受模型单方面落库 |
| 候选列表/更新/忽略 | 只操作当前账号候选；默认只返回 `pending` |
| 候选转正 | 原子地创建或关联正式档案，再将候选改为 `converted`；失败时候选保持 `pending` |
| 聊天请求 | 仅接受已选择的正式档案 ID；候选 ID 不能作为 `profile_ids` 传入 |

## 8. UI/交互要求

- 档案模块使用面向高频操作的紧凑列表，不把整页设计成营销式卡片墙。
- 每位正式人物在独立档案模块中清晰展示姓名、关系、出生资料完整度和排盘状态；编辑与删除使用带图标的次级操作。
- “本人档案”应有稳定且清晰的视觉标识，但不得与其他档案产生功能上的隐式优先级。
- 空状态只呈现当前上下文最需要的操作：无本人档案时优先“创建本人档案”，无其他档案时可“新增人物”，无候选时不展示冗余说明。
- 待补充条目需明确标记为“尚未保存到档案”，避免用户误解；默认只展示最少来源信息，点击后才进入完整处理流程。
- 表单应按“基础信息、出生信息、出生地”分组；出生日期和时间使用受限控件，农历时才显示闰月字段。
- 所有操作都需具备加载、成功、失败、空列表、权限失效和冲突状态。登录过期后保留未提交表单和当前输入草稿，重新登录后允许继续。

### 8.1 桌面端聊天选择器

- 当前对话框左侧入口继续使用人物/档案图标并显示已选数量；点击后打开紧凑弹层，标题为“选择本轮人物”。
- 弹层条目只展示姓名、与本人关系、出生资料完整度和选择状态；整行可选择，支持键盘聚焦、空格切换与 `Esc` 关闭。
- 底部固定操作仅包含“清空”和“确认”；没有档案时只显示“暂无可选档案”，不提供新增、编辑或跳转管理入口。
- 弹层尺寸保持稳定，档案较多时仅列表区域滚动，勾选状态或文本变化不能导致弹层宽高跳动。

### 8.2 手机端入口与选择 UI

- 手机端聊天输入区上方或工具栏提供人物/档案图标入口，并显示已选数量；入口不得挤占发送按钮和文本输入区域。
- 点击入口打开底部抽屉，标题为“选择本轮人物”。抽屉只支持查看、勾选、取消、清空和确认，不提供任何新增或编辑入口。
- 抽屉最大高度不超过可视区域的 70%，顶部标题和底部操作固定，中间列表独立滚动；需适配安全区、软键盘和横竖屏切换。
- 每个可点击目标至少 44 x 44 CSS 像素；姓名过长时换行或省略但不能遮挡关系与勾选状态。
- 手机端独立人物档案入口放在应用主导航或账号菜单中，名称为“人物档案”，使用与桌面一致的人物/档案图标。该入口进入全屏管理页面，不通过聊天选择抽屉承载管理功能。

### 8.3 手机端人物档案模块

- 使用全屏页面承载“档案概览、我的档案、待补充、回收站”，通过顶部返回、页签或分段控件切换，不使用嵌套弹窗堆叠管理流程。
- 页面顶部提供带加号图标的新增入口；创建和编辑使用独立全屏页面，保存或取消后返回原列表并保持原滚动位置和筛选状态。
- 档案列表以紧凑行展示关键信息，次要操作收纳到单条档案的更多菜单；危险操作必须二次确认。
- 待补充数量使用数字标记；表单采用单列布局，底部保存操作固定并避开系统安全区，错误信息显示在对应字段附近。

## 9. 异常与边界

| 场景 | 预期行为 |
| --- | --- |
| 创建第二个有效本人档案 | 阻止保存，提示已有本人档案并提供跳转编辑入口 |
| 候选与现有正式档案同名且同关系 | 转正前提示可能重复，允许用户取消、编辑候选或确认新建；不得静默覆盖现有档案 |
| 候选转正时网络失败 | 候选保持待处理，表单数据在本地短暂保留，可重试 |
| 对话识别错误 | 用户可以忽略或编辑；不能影响正式档案和当前分析结果 |
| 出生信息不完整 | 允许保存基础档案，但显示未完成，排盘/依赖出生资料的分析要引导补齐 |
| 删除当前已附加档案 | 立即从选择器和后续消息上下文移除；历史消息仍显示快照 |
| 恢复本人档案遇到冲突 | 不恢复并提示先处理现有本人档案 |
| 用户提及多个新人物 | 分别生成候选提示，用户可逐一处理；同一轮最多展示 3 个提示，其余进入可查看的候选建议区 |

## 10. 验收标准

### 10.1 本人档案引导

- [ ] 当前账号没有有效本人档案时，进入档案模块会看到本人建档入口。
- [ ] 在没有本人档案时发起需要本人出生资料的分析，用户能选择表单填写、通过对话创建或暂不创建。
- [ ] 表单建档成功后，当前问题未丢失，且新建本人档案自动附加到当前会话。
- [ ] 在任何需要人物资料、排盘或人物分析的对话中，系统会先要求用户明确输入分析对象姓名；关系称谓、代词、`未命名`或系统默认名称均不能替代姓名。
- [ ] 用户输入姓名后，系统会要求其确认该人物与本人的关系，并只按固定 `relationship_type` 枚举保存；称谓识别结果、性别或上下文不能自动决定关系。
- [ ] 无法匹配预置枚举的关系必须保存为 `其他` 并填写关系说明；关系未确认时，不能创建正式档案、调用排盘或保存计算结果。
- [ ] 对话式建档不会在资料缺失时排盘，不会默认出生时间、地点或闰月；用户确认后才保存。
- [ ] 同一会话中关闭引导后，普通闲聊不会重复弹出引导。

### 10.2 待补充人物

- [ ] 用户在消息中明确提及新的非本人对象时，系统只给出非阻塞建议，不自动创建正式档案。
- [ ] 点击“加入待补充”后，候选出现在待补充列表；关闭或忽略提示不会创建正式档案。
- [ ] 同一账号、同一会话、相同名称与关系的候选不会重复创建或重复提示。
- [ ] 候选可编辑名称和关系、可忽略、可通过表单或对话补充；候选不能出现在档案选择器中。
- [ ] 候选转正成功后，正式档案可在“我的档案”看到，候选不再出现在默认待补充列表。
- [ ] 候选转正失败时，不产生半成品正式档案，候选仍可重试。

### 10.3 档案一致性与权限

- [ ] 一个账号同时最多有一个有效本人档案；创建、编辑、恢复均校验该约束。
- [ ] 修改出生日期、时间、历法、地点或经度后，旧四柱、五行和排盘上下文均失效。
- [ ] 已删除档案不会出现在默认列表、选择器、候选去重结果或 Agent 上下文中；恢复后才可重新使用。
- [ ] 用户无法通过修改档案 ID、候选 ID、会话 ID 或请求体读取、修改、删除其他账号的数据。
- [ ] 聊天运行时只使用用户显式选择且服务端校验有效的正式档案；候选和已删除档案绝不被隐式注入。

### 10.4 体验与回归

- [ ] 档案列表、待补充列表、回收站、创建/编辑表单均具备空、加载、失败和成功状态，文本可理解且操作可恢复。
- [ ] 桌面端当前对话框左侧档案弹层只支持选择、取消、清空和确认，界面及键盘操作均不能触发新增、编辑、删除、恢复、复制或候选处理。
- [ ] 手机端聊天档案底部抽屉只支持选择操作；独立“人物档案”入口可进入全屏管理模块完成新增、编辑、删除、恢复和候选处理。
- [ ] 在桌面和移动宽度下，列表行、表单控件和操作按钮不发生遮挡、截断或不可点击，手机端触控目标不小于 44 x 44 CSS 像素。
- [ ] 从人物档案模块主动新增或编辑档案不会隐式改变任何聊天的已选档案；由聊天缺档引导创建成功时能准确返回原对话并附加新档案。
- [ ] 现有档案创建、编辑、选择、软删除、恢复、排盘结果保存及历史会话展示行为不回归。

## 11. 后续迭代（P1）

P1 依赖 P0 的正式档案、候选人物、账号归属和软删除能力已稳定上线。P1 不改变 P0 的核心原则：用户确认优先、档案与长期记忆隔离、账号数据严格隔离。

### 11.1 候选人物增强

- 提供候选历史视图，包含 `pending`、`converted` 和 `dismissed` 三种状态；默认仍只展示待处理候选。
- 支持按名称、关系、状态、来源会话和最近提及时间搜索、筛选与排序。
- 支持批量忽略、批量恢复已忽略候选，以及将多个重复候选合并为一个待处理候选。
- 系统可以基于用户已确认的名称、关系和已存在档案给出去重建议，但不得自动合并、自动忽略或自动创建档案。
- 合并时保留所有来源会话/消息引用和最近提及时间；被合并候选标记为 `merged` 并指向保留候选，避免重复计数。

### 11.2 档案组织与完善度

- 正式档案支持自定义分组、标签、头像和备注。分组与标签仅用于当前账号内的组织与检索，不改变关系类型、排盘规则或 Agent 上下文。
- 每份档案展示资料完整度：基础身份、出生日期、出生时间、历法、出生地和已排盘状态；只提示完成下一步所需字段，不以百分比制造误导性精确度。
- 提供“待完善”筛选与任务清单；点击任务直接进入对应表单字段或对话补充流程。
- 备注按用户私密资料处理，不默认注入 Agent；用户须在当前会话主动选择“附带备注”后才可加入上下文，并需在输入区明确显示。
- 头像只接受受支持格式、尺寸和文件大小范围；服务端验证内容类型，访问权限与对应档案一致。

### 11.3 档案文本复制

- 在每个有效正式档案的详情和列表操作区提供“复制档案文本”操作；复制结果写入用户设备剪贴板，不创建文件、不调用导入导出接口，也不写回服务端。
- 复制内容为可直接粘贴到聊天、备忘录或其他应用的纯文本，采用稳定的“字段名：字段值”格式，至少包含姓名、关系、性别、出生日期、出生时间、历法、出生地、四柱、五行和资料/排盘状态；未填写字段显示“未填写”，不补造默认值。
- 复制内容只包含当前用户在界面可见的档案资料，不包含档案 ID、账号 ID、`source_session_id`、来源消息 ID、创建/更新时间、删除状态、内部计算原始数据、长期记忆或完整对话正文。
- 备注默认不包含在复制文本中；用户可在复制前显式勾选“包含备注”，并在勾选时看到提示该内容可能含有个人信息。
- 已删除档案和待补充候选不提供复制完整档案文本；候选可复制其名称与关系，且文本必须明确标记“待补充，尚未保存为正式档案”。
- 剪贴板权限被浏览器拒绝或复制失败时，展示可选中、可手动复制的文本预览，并给出失败提示；不得静默丢失复制结果。

### 11.4 对话提取的待确认字段

- 系统可从用户明确提供的聊天内容中提取候选字段，如姓名、关系、出生日期、出生时间、历法与出生地，并以“待确认字段”形式展示。
- 每个候选字段必须展示来源消息的最小必要摘录与置信提示；用户可逐项确认、修改或忽略。未确认字段不得写入正式档案或用于排盘。
- 与现有档案字段冲突时，系统显示差异并要求用户选择保留已有值或使用新值；不得依据模型置信度自动覆盖。
- 用户可在设置中关闭对话字段提取。关闭后不再生成新字段建议，已有候选不受影响。

### 11.5 P1 验收标准

- [ ] 用户可搜索、筛选、批量处理和恢复候选；系统给出去重建议但不会自动合并或自动建档。
- [ ] 合并候选后，保留候选仍可追溯全部来源，被合并候选不再在默认列表重复出现。
- [ ] 用户可为自有档案添加分组、标签、头像和备注；备注默认不进入 Agent 上下文。
- [ ] 用户可将有效正式档案复制为可读纯文本，复制结果包含可见资料字段，不包含内部标识、来源会话、长期记忆或对话正文。
- [ ] 备注只有在用户显式勾选后才会包含在复制文本中；剪贴板复制失败时，用户仍能从文本预览手动复制。
- [ ] 待补充候选只能复制名称和关系，且复制文本明确标记为未保存；已删除档案不提供复制操作。
- [ ] 每个对话提取字段均需用户逐项确认后才能写入档案；用户关闭该能力后不再产生新建议。
